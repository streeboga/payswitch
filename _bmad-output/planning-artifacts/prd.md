# Product Requirements Document - payswitch

**Автор:** K.mazurov
**Дата:** 2026-03-18

## Резюме

Payswitch — self-hosted платёжный оркестратор на PHP/Laravel с Hyperswitch-совместимым REST API, предназначенный для рынка СНГ. Продукт решает проблему отсутствия доступного payment switch для локальных платёжных систем (ЮKassa, CloudPayments, Тинькофф и др.), которые не поддерживаются западными оркестраторами вроде Hyperswitch. Целевые пользователи — команды, разрабатывающие сервисы для рынка СНГ, которым необходим полный контроль над платёжной инфраструктурой: единый API для маршрутизации платежей через несколько процессоров, self-hosted деплой и возможность быстро добавлять новые интеграции.

### Ключевые отличия

- **PHP/Laravel стек** — в отличие от Hyperswitch (Rust), payswitch работает на стеке, привычном большинству команд в СНГ, с низким порогом входа для кастомизации и расширения
- **OmniPay-PHP для интеграций** — добавление нового платёжного провайдера сводится к подключению OmniPay-драйвера, без необходимости писать низкоуровневые адаптеры
- **Фокус на СНГ** — поддержка локальных процессоров, которых нет в Hyperswitch, при сохранении совместимости с его API для использования западных PSP
- **Self-hosted** — полный контроль над данными и транзакциями, критичный для соответствия локальным регуляторным требованиям

## Классификация проекта

- **Тип:** API Backend (REST API, Hyperswitch-совместимый)
- **Домен:** Fintech (платёжная оркестрация, мульти-процессорная маршрутизация)
- **Сложность:** Высокая (PCI DSS, безопасность платёжных данных, state machine транзакций, мультитенантность)
- **Контекст:** Brownfield (расширение существующего приложения на Laravel 13 + React 19)

## Критерии успеха

### Успех пользователей

- Разработчики интегрируют API payswitch и проводят первый тестовый платёж в течение 1 часа после установки
- Добавление нового платёжного коннектора занимает менее 4 часов разработки с использованием паттерна OmniPay-драйвера
- Мерчанты управляют коннекторами, API-ключами и бизнес-профилями через API без ручного вмешательства
- Жизненный цикл платежа (create → confirm → capture → refund) корректно завершается на всех подключённых процессорах

### Бизнес-успех

- MVP поддерживает минимум 3 СНГ-процессора (ЮKassa, CloudPayments, Тинькофф) и 2 западных (Stripe + любой другой)
- Система обрабатывает платежи достаточно надёжно для использования в продакшене собственного сервиса
- Платёжная маршрутизация успешно переключается на резервный коннектор при отказе основного
- Система обрабатывает минимум 100 одновременных платёжных операций без деградации

### Технический успех

- Совместимость с API Hyperswitch: клиенты, использующие Hyperswitch API, могут перейти на payswitch с минимальными изменениями кода
- State machine платежа обеспечивает корректные переходы статусов, предотвращая невалидные операции (например, capture уже отменённого платежа)
- Доставка webhook-ов достигает 99%+ успешности в пределах 24-часового окна ретраев
- Все платёжные credentials хранятся в зашифрованном виде; никаких plaintext-секретов в БД или логах

### Измеримые результаты

- Время ответа API при создании платежа: < 500мс (без учёта задержки PSP)
- Покрытие state machine: 100% базовых статусов Hyperswitch реализовано
- Покрытие тестами жизненного цикла платежа: > 90%
- Ноль утечек данных или credentials за первые 12 месяцев

## Scope продукта

### MVP — Минимально жизнеспособный продукт

- Система аутентификации: Admin API Key, Secret API Key, Publishable Key с автоматическим определением merchant_id
- Полный жизненный цикл платежей: POST /payments (создание), POST /payments/{id}/confirm, POST /payments/{id}/capture, POST /payments/{id}/cancel, GET /payments/{id}
- Рефанды: POST /refunds, GET /refunds/{id}
- CRUD клиентов: POST /customers, GET /customers/{id}, POST /customers/{id} (обновление), DELETE /customers/{id}
- Провизионирование мерчантов через Admin API: организации, merchant accounts, бизнес-профили, API-ключи, управление коннекторами
- State machine платежа со всеми базовыми переходами статусов
- Интеграционный слой OmniPay: коннектор Stripe + 1 СНГ-коннектор (ЮKassa)
- Webhook-и с HMAC-SHA512 подписью и политикой ретраев
- Single routing (явный выбор коннектора) и priority-based fallback
- Генерация client secret для совместимости с фронтенд-SDK

### Функции роста (Post-MVP)

- Дополнительные СНГ-коннекторы: CloudPayments, Тинькофф, Robokassa, PayKeeper
- Методы оплаты помимо карт: банковские переводы, электронные кошельки, QR-коды (СБП)
- 3DS аутентификация с обработкой редиректов
- Управление методами оплаты и сохранённые карты (setup_future_usage)
- Поддержка мандатов для рекуррентных платежей
- Эндпоинты списков платежей и рефандов с фильтрацией/сортировкой
- Dashboard UI для управления мерчантами (React-фронтенд)
- Ephemeral-ключи для ограниченных клиентских операций

### Видение (будущее)

- Smart routing: разделение по объёму, rule-based, маршрутизация по проценту успешности
- Мультивалютная поддержка с автоматической конвертацией
- Управление диспутами/чарджбэками
- Интеграция с системами фрод-детекции
- Аналитический дашборд с отчётами
- SDK для фронтенд-форм оплаты (JS SDK, мобильные SDK)
- Поддержка маркетплейсов/сплит-платежей
- Путь к сертификации PCI DSS Level 1

## Пользовательские сценарии

### Сценарий 1: Разработчик — первая интеграция (успешный путь)

**Антон**, бэкенд-разработчик в СНГ-стартапе электронной коммерции. Ему нужно принимать платежи от российских и международных клиентов. Сейчас использует ЮKassa напрямую, но нужно добавить Stripe для международных карт.

**Начальная сцена:** Антон находит payswitch, клонирует репо, запускает `composer setup`. Читает документацию API, построенную по модели Hyperswitch — знакомые Stripe-подобные паттерны. Создаёт merchant account, генерирует API-ключи и подключает оба коннектора — ЮKassa и Stripe — через Admin API.

**Развитие:** Антон отправляет первый `POST /payments` с суммой и валютой. Получает payment_id и client_secret. Отправляет `POST /payments/{id}/confirm` с данными карты через ЮKassa — платёж переходит в `processing`, затем в `succeeded`. Тестирует тот же flow через Stripe, указав коннектор. Оба работают идентично.

**Кульминация:** Антон настраивает приоритетную маршрутизацию: ЮKassa первой для RUB-платежей, Stripe для USD. Когда ЮKassa возвращает ошибку, система автоматически повторяет через Stripe. Первая реальная транзакция проходит бесшовно.

**Развязка:** Сервис Антона обрабатывает платежи через единый API. Добавление нового процессора в будущем потребует только подключения нового OmniPay-драйвера — без изменений в интеграционном коде.

### Сценарий 2: Разработчик — обработка ошибок (edge case)

**Антон** получает webhook-уведомление о неудачном платеже. Проверяет `GET /payments/{id}` — статус `failed` с `error_code` и `error_message` от процессора. Создаёт новую попытку оплаты для того же заказа, указав альтернативный коннектор. Платёж проходит успешно. Реализует retry-логику в своём сервисе, используя статусные колбэки.

Клиент запрашивает частичный возврат. Антон отправляет `POST /refunds` с payment_id и частичной суммой. Рефанд обрабатывается через тот же коннектор, что обработал исходный платёж. Проверяет через `GET /refunds/{id}`, что статус — `succeeded`.

### Сценарий 3: Системный администратор — онбординг мерчанта

**Мария**, руководитель операций, должна подключить новый бизнес-юнит, который принимает платежи независимо.

**Начальная сцена:** Мария использует Admin API Key для создания новой организации и merchant account. Генерирует publishable key для фронтенда и secret key для бэкенда.

**Развитие:** Создаёт бизнес-профиль с webhook URL и настраивает payment_response_hash_key. Подключает два коннектора — ЮKassa для внутренних и Stripe для международных платежей — указывая методы оплаты, карточные сети и лимиты сумм для каждого.

**Кульминация:** Мария генерирует API-ключи для команды разработки нового мерчанта, отправляет им credentials и документацию API. Команда начинает интеграцию немедленно, используя те же паттерны, что и существующий мерчант.

**Развязка:** Новый бизнес-юнит работает независимо со своими коннекторами, профилями и API-ключами — всё управляется через один инстанс payswitch.

### Сценарий 4: API-потребитель — интеграция webhook-ов

**Сергей**, бэкенд-разработчик, которому нужны надёжные уведомления о статусе платежей.

Настраивает webhook URL в бизнес-профиле. Когда платёж переходит в `succeeded`, payswitch отправляет HTTP POST с объектом платежа в теле, подписанным HMAC-SHA512 в заголовке `x-webhook-signature-512`. Сервис Сергея верифицирует подпись через `payment_response_hash_key`, обрабатывает событие и возвращает HTTP 200.

Если сервер временно недоступен, payswitch ретраит: 1 минута, затем 5 минут, затем 10 минут, с эскалацией в течение 24 часов. Сергей использует `event_id` для идемпотентности и timestamp `updated` для обработки событий, пришедших не по порядку.

|----------|----------------------|

| Разработчик — обработка ошибок | Повтор платежа, рефанды, отслеживание статусов, отчётность об ошибках |

## Доменные требования

### Комплаенс и регуляторика

- **PCI DSS:** Данные карт никогда не хранятся в plaintext. В MVP payswitch работает как pass-through — карточные данные отправляются напрямую в PSP через OmniPay. Хранение карт на этапе MVP не предусмотрено.
- **152-ФЗ (Закон о персональных данных):** Self-hosted деплой обеспечивает хранение персональных данных на российских серверах при необходимости.
- **Безопасность PSP credentials:** Учётные данные коннекторов (API-ключи, merchant accounts) хранятся в зашифрованном виде в БД с использованием шифрования Laravel.
- **Аудит-трейл:** Все переходы статусов платежа логируются с timestamps, актором и предыдущим/новым статусом.

### Технические ограничения

- **Шифрование at rest:** Все чувствительные поля (credentials коннекторов, хэши API-ключей) зашифрованы AES-256-CBC через фасад `Crypt` Laravel.
- **Шифрование in transit:** Все API-эндпоинты требуют HTTPS. HTTP-фолбэк отключён.
- **Безопасность API-ключей:** Secret-ключи хранятся как bcrypt-хэши. В plaintext хранится только префикс для идентификации. Полный ключ показывается только один раз при создании.
- **Идемпотентность:** Создание платежа поддерживает идемпотентный `payment_id` для предотвращения дублирования списаний.

### Требования к интеграциям

- **OmniPay-PHP:** Все PSP-интеграции проходят через интерфейс OmniPay gateway. Каждый коннектор маппится на OmniPay-пакет.
- **Совместимость с API Hyperswitch:** Форматы запросов/ответов следуют конвенциям Hyperswitch REST API. Клиенты, мигрирующие с Hyperswitch, должны требовать минимальных изменений кода.
- **Исходящие webhook-и:** HTTP POST на URL, настроенный мерчантом, с HMAC-SHA512 подписью и экспоненциальным бэкофф-ретраем.

### Митигация рисков

| Риск | Митигация |
|------|-----------|
| Отсутствие OmniPay-драйвера для СНГ-процессора | Написание кастомного OmniPay-драйвера по интерфейсу gateway; community-пакеты существуют для ЮKassa, CloudPayments |
| Платёж застрял в промежуточном статусе | State machine обеспечивает валидные переходы; фоновый job мониторит зависшие платежи и помечает их как expired |
| Сбой доставки webhook-а | 16 попыток ретрая в течение 24 часов; таблица webhook_events отслеживает статус доставки |
| Утечка credentials | Шифрованное хранение, API-ключи только в виде хэшей, аудит-логи, никакого plaintext в логах |

## Специфические требования API Backend

### Архитектура API

- **Протокол:** REST поверх HTTPS, JSON тела запросов/ответов
- **Базовый путь:** Настраиваемый (по умолчанию: `/api/v1`)
- **Аутентификация:** Три типа ключей через заголовок `api-key` — Admin API Key (конфигурационная константа), Secret API Key (хэшированный, per-merchant), Publishable Key (per-merchant, ограниченный scope)
- **Определение мерчанта:** Merchant ID определяется автоматически из API-ключа — никогда не передаётся явно в запросах
- **Формат ошибок:** Единообразные JSON-ответы с полями `error.type`, `error.code`, `error.message`
- **HTTP-коды:** 200 (успех), 400 (валидация), 401 (не авторизован), 404 (не найден), 500 (серверная ошибка)

### Спецификация эндпоинтов

**Платежи (ядро):**
- `POST /payments` — создание PaymentIntent
- `POST /payments/{id}/confirm` — подтверждение с данными метода оплаты
- `POST /payments/{id}/capture` — захват авторизованных средств (manual capture)
- `POST /payments/{id}/cancel` — отмена платежа
- `GET /payments/{id}` — получение статуса платежа

**Рефанды:**
- `POST /refunds` — создание рефанда
- `GET /refunds/{id}` — получение рефанда

**Клиенты:**
- `POST /customers` — создание клиента
- `GET /customers/{id}` — получение клиента
- `POST /customers/{id}` — обновление клиента
- `DELETE /customers/{id}` — удаление клиента

**Управление аккаунтами (требует Admin API Key):**
- `POST /organization` — создание организации
- `POST /accounts` — создание merchant account
- `GET /accounts/{id}` — получение merchant account
- `POST /profiles` — создание бизнес-профиля
- `GET /profiles/{id}` — получение бизнес-профиля
- `POST /api_keys/{merchant_id}` — создание API-ключа
- `POST /account/{merchant_id}/connectors` — добавление коннектора
- `GET /account/{merchant_id}/connectors` — список коннекторов

**Webhook-и:**
- `POST /webhooks/{merchant_id}/{merchant_connector_id}` — входящий webhook от PSP

### Генерация ID

- Payment ID: `pay_` + 26 буквенно-цифровых символов
- Customer ID: `cus_` + буквенно-цифровые символы (1-64 символа)
- Refund ID: `ref_` + буквенно-цифровые символы
- Profile ID: `pro_` + буквенно-цифровые символы
- Merchant Connector ID: `mca_` + буквенно-цифровые символы
- Client Secret: `{payment_id}_secret_{random_string}`
- Префикс API Key: `snd_` (sandbox) / `prod_` (production)

### State machine платежа

```
requires_payment_method → requires_confirmation → processing → succeeded
                                                → requires_capture → succeeded
                                                → requires_customer_action → processing
                                                → failed (retryable)
                        → cancelled
                        → expired
```

Валидные переходы обеспечиваются на уровне приложения. Попытки невалидных переходов возвращают HTTP 400.

### Особенности реализации

- **Паттерн Laravel Actions:** Платёжные операции (create, confirm, capture, cancel, refund) реализуются как Action-классы
- **Маппинг OmniPay Gateway:** Каждая запись коннектора маппится на класс OmniPay gateway. `capture_method: automatic` → `purchase()`, `capture_method: manual` → `authorize()` + `capture()`
- **БД:** PostgreSQL рекомендуется для поддержки JSON-колонок (credentials коннекторов, metadata, payment_methods_enabled). SQLite для тестирования.
- **Очередь:** Переходы статусов платежей и доставка webhook-ов диспатчатся через Laravel Queue (database-драйвер для MVP)

- Smart routing (разделение по объёму, rule-based)
- Управление диспутами
- Аналитический дашборд
- JS SDK для платёжных форм
- Мультивалютная конвертация
- Маркетплейс/сплит-платежи

### Стратегия митигации рисков

**Технические риски:** Доступность OmniPay-драйверов для СНГ-процессоров — митигируется написанием кастомных драйверов по интерфейсу OmniPay gateway. Сложность state machine — митигируется всесторонними Pest-тестами для каждого перехода.

**Рыночные риски:** СНГ-процессоры могут изменить API — митигируется абстракционным слоем OmniPay, изолирующим изменения на уровне драйвера.

**Ресурсные риски:** MVP ограничен только API (без фронтенда), минимум 2 коннектора. Можно запуститься даже с 1 коннектором при необходимости.

## Функциональные требования

### Аутентификация и авторизация

- FR1: Система определяет идентичность мерчанта из API-ключа автоматически без явного merchant_id в запросах
- FR2: Админ может аутентифицироваться Admin API Key для выполнения операций провизионирования тенантов
- FR3: Бэкенд мерчанта может аутентифицироваться Secret API Key для выполнения платёжных операций
- FR4: Клиентские приложения могут аутентифицироваться Publishable Key для операций ограниченного scope
- FR5: Система валидирует формат API-ключа и отклоняет истёкшие или отозванные ключи с соответствующими кодами ошибок

### Платёжные операции

- FR6: Мерчант может создать PaymentIntent с суммой и валютой, получив payment_id и client_secret
- FR7: Мерчант может подтвердить платёж, предоставив данные метода оплаты (данные карты)
- FR8: Мерчант может захватить авторизованные средства (manual capture) с указанной суммой
- FR9: Мерчант может отменить платёж, который не был захвачен
- FR10: Мерчант может получить статус и детали платежа по payment_id
- FR11: Система обеспечивает валидные переходы статусов платежа и отклоняет невалидные операции
- FR12: Система поддерживает automatic capture (confirm → processing → succeeded) и manual capture (confirm → requires_capture → capture → succeeded)
- FR13: Мерчант может создать платёж с `confirm: true` для объединения создания и подтверждения в одном вызове
- FR14: Система генерирует уникальные ID платежей в формате `pay_` и client secrets в формате `{payment_id}_secret_{random}`
- FR15: Система отслеживает количество попыток оплаты и поддерживает несколько попыток на один PaymentIntent

### Операции рефандов

- FR16: Мерчант может создать полный или частичный рефанд для успешного платежа
- FR17: Мерчант может получить статус и детали рефанда по refund_id
- FR18: Система направляет рефанд через тот же коннектор, который обработал исходный платёж
- FR19: Система генерирует уникальные ID рефандов в формате `ref_`

### Управление клиентами

- FR20: Мерчант может создать клиента с опциональным кастомным ID, именем, email, телефоном и metadata
- FR21: Мерчант может получить детали клиента по customer_id
- FR22: Мерчант может обновить информацию клиента
- FR23: Мерчант может удалить клиента
- FR24: Система автоматически генерирует customer_id в формате `cus_`, если не указан

### Провизионирование мерчантов

- FR25: Админ может создать организацию как верхнеуровневую сущность
- FR26: Админ может создать merchant account в организации, получив merchant_id и publishable_key
- FR27: Админ может создать бизнес-профиль для мерчанта с webhook URL и конфигурацией hash key
- FR28: Админ может сгенерировать API-ключи для мерчанта, с показом полного ключа только при создании
- FR29: Админ может отозвать API-ключи мерчанта
- FR30: Админ может добавить коннектор (PSP) к мерчанту с credentials, методами оплаты и конфигурацией
- FR31: Админ может просматривать, получать, обновлять и удалять коннекторы мерчанта
- FR32: Система хранит credentials коннекторов в зашифрованном виде

### Маршрутизация платежей

- FR33: Мерчант может указать конкретный коннектор для платежа (явная маршрутизация)
- FR34: Система поддерживает priority-based fallback коннекторов при отказе основного
- FR35: Система выбирает подходящий коннектор на основе метода оплаты и валюты, если не указан явно

### Управление webhook-ами

- FR36: Система отправляет webhook-уведомления на URL, настроенный мерчантом, при изменении статуса платежа
- FR37: Система подписывает webhook payload с HMAC-SHA512, используя payment_response_hash_key бизнес-профиля
- FR38: Система повторяет неудачные доставки webhook-ов по экспоненциальному бэкофф-расписанию в течение 24 часов
- FR39: Система включает уникальный event_id для идемпотентной обработки webhook-ов
- FR40: Система отслеживает статус доставки webhook-а по каждому событию (delivered, pending, failed)

### Интеграция коннекторов

- FR41: Система интегрируется с платёжными процессорами через интерфейс OmniPay gateway
- FR42: Система маппит операции Hyperswitch-коннекторов на методы OmniPay (purchase, authorize, capture, refund)
- FR43: Система поддерживает коннектор Stripe через OmniPay
- FR44: Система поддерживает коннектор ЮKassa через OmniPay
- FR45: Система нормализует PSP-специфичные коды ошибок в единообразный Hyperswitch-совместимый формат

## Нефункциональные требования

### Производительность

- Время ответа API при создании платежа (без учёта задержки PSP): < 500мс на 95-м перцентиле
- Время ответа API для операций чтения (GET-эндпоинты): < 200мс на 95-м перцентиле
- Инициация доставки webhook-а: в течение 5 секунд после изменения статуса платежа
- Система поддерживает 100 одновременных платёжных операций без деградации

### Безопасность

- Все API-эндпоинты работают только по HTTPS; HTTP-запросы отклоняются
- Credentials коннекторов зашифрованы at rest с использованием AES-256-CBC
- Secret API-ключи хранятся как bcrypt-хэши; plaintext показывается только при создании
- Данные платёжных карт не хранятся в системе — только pass-through к PSP
- Все переходы статусов платежа логируются с timestamp, актором, предыдущим и новым статусом
- Префиксы API-ключей хранятся в plaintext для идентификации; хэш используется для аутентификации
- Поля metadata валидируются: максимум 50 ключей, длина ключа до 40 символов, длина значения до 500 символов

### Масштабируемость

- Горизонтальное масштабирование: stateless API-слой, всё состояние в БД
- Доставка webhook-ов через очередь, отделённая от обработки платежей
- БД спроектирована для партиционирования по merchant_id для будущего масштабирования
- Система поддерживает 10-кратный рост объёма транзакций через горизонтальное масштабирование подов

### Интеграция

- Wire-совместимость с API Hyperswitch: JSON-структура запросов/ответов соответствует конвенциям Hyperswitch
- Соответствие интерфейсу OmniPay gateway для всех коннекторных интеграций
- Стандартная HTTP-доставка webhook-ов с настраиваемыми URL per business profile
- Поддержка подписей HMAC-SHA512 и HMAC-SHA256 для верификации webhook-ов
