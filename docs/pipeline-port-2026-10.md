# Перенос работы конвейера на боевой код (05.10.2026)

Ветка `feat/pipeline-port-2026-10-05` от `origin/main` (`4c7ab13`). Источник —
`chore/worktree-2026-10-05` (`9d2626b`), семь коммитов поверх main 56-коммитной
давности. Слияние не делалось: логика перенесена заново на классы main.

Правило переноса: всё, что Genesis уже получает от main, осталось как на main —
422 `idempotency_key_reused`, 502 `refund_pending`, ключ идемпотентности только
заголовком, параметр `refund_id` у провайдера, три защиты `ResolveApiKey`, обе
подписи исходящих вебхуков.

### Хэш тела запроса

В хэш не входят сам ключ и `payment_method_data` (хэш номера карты в базе — тот же
номер для перебора); порядок ключей не важен. У строк, созданных до миграции, хэша
нет — их повтор сравнивается по-прежнему. У возврата тело сегодня — платёж и сумма,
их и так сравнивает main; хэш возврата начнёт что-то значить, когда запрос станет
принимать `reason` и `metadata`.

Перед включением: в логе не должно быть `Idempotency-Key replayed with a different
request body` — иначе чей-то повтор (например, с новым `return_url`) начнёт получать 422.

### Сверка возвратов

Берёт pending-возвраты, которым провайдер уже дал свой id (`connector_refund_id`),
не тронутые от 2 минут до 14 дней. Итог пишется, только если провайдер называет тот
же платёж, сумму и валюту; иначе — `Log::error`, возврат остаётся pending.

Чего не делает:

- возврат без id провайдера (таймаут до ответа) не сверяет — его закрывает
  уведомление провайдера или человек;
- отвечать умеет только YooKassa (`RefundStatusQueryable`). У CloudPayments, который
  один сейчас разрешён к подключению (`PAYSWITCH_CONNECTABLE`), чтения возврата нет.

### Миграции

- `2026_10_06_000100` — nullable `request_hash` на `payment_intents` и `refunds`,
  без значения по умолчанию и без индекса.
- `2026_10_06_000200` — пять новых таблиц `payout_*`.

Колонок и индексов, которые main уже создал (`idempotency_key`), нет.

## Что не перенесено и почему

| Из конвейера | Причина |
|---|---|
| Поиск ключа API по полному хэшу | есть на main (`a188f20`) вместе с типом ключа, лимитом по IP и запретом слабого admin-ключа |
| 409 `idempotency_conflict`, ключ из тела запроса | контракт main: 422 и только заголовок |
| Неизвестный исход возврата молча pending, параметр `idempotency_key` у провайдера | контракт main: 502 `refund_pending`, `refund_id` (`b06d511`, `8c5b392`) |
| Блокировка мерчанта на создании платежа | main разводит гонку уникальным индексом (`f292951`); блокировка ставила бы все платежи мерчанта в очередь |
| Подпись вебхука с меткой времени, `updated` из `created_at` | есть на main (`5651165`, `e7c2621`) |
| 503 провайдеру на любой отказ приёмника | main отвечает 500, только когда исход не записан (`9e77a25`); 503 на чужой платёж заставил бы провайдера повторять вечно |
| Отказ от перехода к другому PSP после таймаута, истечение под блокировкой | есть на main (`b870339`, `71eec97`) |
| Колонки времени события у возврата, закрепление подключения в попытке | ничем на main не читаются |

## Решения владельца (постановка)

1. **Идемпотентность capture/cancel** (`PaymentActionService`, `pending_action`).
   Сейчас неизвестный исход capture — 502 `capture_failed`, платёж остаётся
   `requires_capture` и чинится уведомлением провайдера. В конвейере — платёж с
   «действием в ожидании» и повтор по ключу. Это другой ответ Genesis на тот же
   запрос, а не добавление.
2. **Бизнес-идентичность платежа** (`project_id`, `operation_id`, `order_id` в
   запросе, ответе и событии). Новые поля контракта, которые Genesis не шлёт и не
   читает; назначение сейчас едет в `metadata`.
3. **Координатор исполнения и маршруты `execution-authorizations`.** Зависит от
   пунктов 1 и 2; зачисление в коде конвейера работает только при `APP_ENV=testing`,
   маршруты всегда отвечают 503, протокол с Genesis не согласован
   (`original-intent-authorization-v1`).
